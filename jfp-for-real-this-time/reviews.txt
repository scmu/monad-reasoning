> Comments to the Author
>
> # Summary
>
> There exist two types of effect interactions between state and nondeterminism:
> global and local states. A global state carries a single state across all
> nondeterministic branches, whereas local states offer each branch its own state
> copy. Local states are good for reasoning, while global states prove
> advantageous for performance.
>
> This paper studies global states, local states, and non-determinism through
> three key steps:
>
> 1. Translation of local state to global state
> 2. Translation of non-determinism to global state
> 3. Merging two states to a single state of tuples
>
> At this point, one can implement non-determinism and local states using global
> states.
>
> The paper further improves the efficiency of the approach, by refining step 1
> through two more efficient implementations using
>
> (a) Updates and restoration: instead of explicitly copying the local-state
> semantics into the global-state semantics, this approach keeps track of the
> state modifications and undoes them when necessary.
>
> (b) Trail stack: a technique that batches consecutive restorative steps.
>
> The framework is built on top of effect handlers implemented as free monads,
> demonstrating equivalence properties through program calculation and fusion
> laws.
>
> Overall, this is a fun paper to read, and aligns well with JFP's scope.
>
> # Comments
>
> I have two main comments regarding monad instances and effect handlers:
>
> 1. The effect handler interface appears somewhat restricted.
> 2. I am curious about the extent to which the results are specific to algebraic
>   effects and handlers.
>
> ## The effect handler interface
>
> The paper introduces the following monad instance:
>
> ```
> instance (...) => MState s (Free (State s :+: f))
> ```
>
> This interface requires `State s` to be exactly the first effect in the effect
> list. Similarly, the interface
>
> ```
> instance (...) => MNondet (Free (g :+: Nondet :+: f))
> ```
>
> requires `Nondet` to be exactly the second effect in the effect list.
>
> As such, `Free (State s :+: Nondet :+: f)` supports both state and
> nondeterminism, while `Free (Nondet :+: State s :+: f)` does not.
>
> This necessitates the `<=>` function to explicitly swap the order of two
> functors:
>
> ```
> (<=>) :: (...) => Free (f1 :+:f2 :+:f) a -> Free (f2 :+: f1 :+: f) a
> ```
>
> This approach is unsatisfying for two reasons. First, it essentially requires
> the user to explicitly insert coercions to witness the equivalence of effect
> lists. This seems to go against the modularity typically desired in effect
> handler, while being closer to monad transformers that require explicit lifts.
>
> Consequently, this interface tries to achieve a form of modularity using type
> classes. For example, instead of returning `Free ...`, the type of `queens` is:
>
> `queens :: (MState (Int, [Int]) m, MNondet m) => Int -> m [Int]`
>
> However, all `MState` and `MNondet` instances, in my opinion, are quite
> distracting, giving the impression that effect handlers must implement monad
> instances to be effective. Would it be possible to get rid of those monadic
> instances, and instead give an implementation of `queens` based on effect
> operations?
>
> ## Specific to effect handlers
>
> The techniques for implementing local states and non-determinism using global
> states are intriguing.
>
> However, I kept wondering: To what extent are these techniques specific to
> effect handlers per se, considering that many steps apply more general ideas?
> One might implement a monadic interface for `queens` as well as other functions,
> and reason about equivalence between different monadic implementations?
>
> While the paper notes that using effect handlers enable one to make use of the
> fusion laws, it seems to unnecessarily tie results exclusively to effect
> handlers.
>
> While perhaps no fundamental changes are necessary, this is a question worth
> discussing and clarifying in the paper?

Yes, it is possible to make the handler interface more convenient (like the
order of effects / handler applications and an implicit (<=>) operator), but
that is not the focus of our paper. Instead, it is reasoning, which is easier
to do and to understand on a more bare-bones handler interface.

At the same time, we have used type class constraints like MState and MNondet
to leave room for generality. Instantiating these constraints with appropriate
free monads allows for the inductive reasoning and fusion methodology we
employ.  Yet, the results we obtain can also be transferred to other monad
instances, with parametricity as a tool. For instance, through parametricity
we have that, given (p :: MState S m) :: m A and Functor F,

	h_State p = p

where p in the left-hand side has type Free (StateF S :+: F) A) and
in the right-hand side StateT S (Free F) A.

> Referee: 3
>
> Comments to the Author
>
> This paper presents an approach to translate from high-level effects to
> low-level effects. This allows one to write a program using high-level effects,
> but the code can be translated and optimized using low-level effects. The
> high-level effects this paper studies are nondeterminism and local state that
> can viewed as states being duplicated at every nondeterministic branch. The
> low-level effect considered is a single global state. The paper shows how to
> translate programs written in nondeterminism and local state, to an equivalent
> program in global state. There is no performance gained at this step yet, as the
> state is still "duplicated". However, the paper continues to show that, by using a
> structure similar to Prolog's Warren Abstract Machine, the program can be
> optimized because we only keep track of incremental, reversible state updates.
>
> I find this paper generally well-written, easy to follow, and intellectually
> enlightening. Distinguishing effects similarly to how we distinguish
> "high-level" and "low-level" programming is quite novel and the paper makes a
> convincing first step as to why distinguishing these effects can be beneficial in
> programming. I find the work presented in this paper solid and there is
> potential for a series of new research work following this. Besides those main
> strengths, I also appreciate the paper's thoughtful discussion on type-class
> laws.
>
> On the other hand, I am disappointed to see that for a paper that focuses on
> high-level programming with low-level optimizations, there is no experiment to
> show how effective these optimizations are. I believe these questions are
> important to answer: What does the performance look like using high-level
> effects? How much speedup did we gain after optimizations? What about memory
> usage? Furthermore, how does the technique work on other programs that require
> either DFS or BFS with pruning?
